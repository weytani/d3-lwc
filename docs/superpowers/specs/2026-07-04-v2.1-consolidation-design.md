# v2.1.0 Consolidation & Expansion — Design Spec

**Date:** 2026-07-04
**Baseline:** v2.0.0 (`bb67913`), 30 charts, 64 jest suites / 2,573 tests green.
**Scope:** One release containing six workstreams: (1) test-suite trim, (2) quality fixes for the weakest charts, (3) the next 10 charts from CHART-INDEX, (4) GraphQL `fetchMode` on every chart, (5) a comprehensive documentation set, (6) the v2.1.0 release itself.

---

## 1. Goals & Non-Goals

**Goals**

- Reduce test-suite redundancy without losing functional coverage; every component keeps all three tiers (unit, integration, e2e).
- Bring the weakest charts up to the library's current conventions (states, cleanup, no dead surface, shared-helper usage).
- Grow the library 30 → 40 charts following CHART-INDEX build order (#5–#14).
- Make GraphQL self-fetch (`fetchMode`) a library-wide capability, not a bar/gantt special case.
- Ship a documentation set good enough that a new consumer never needs to read component source.
- Release as **v2.1.0** — everything here is additive, so a MINOR bump per semver.

**Non-Goals**

- No B-pattern (breaking, Apex-path-removal) conversions. `d3GanttChart` stays the only replace-style chart; that was an explicit per-chart decision by David for v2.0.0.
- No Apex controller changes. GraphQL mode exists precisely to avoid new Apex; existing endpoints stay untouched.
- No agentforce-dev sync in this release (tracked as a follow-up; the gantt meta.xml hand-merge from v2.0.0 is still pending there too).
- No live-org visual iteration pass on all 40 charts; a sample smoke deploy is the live gate (§7).

## 2. Workstream A — Test trim

Constraints (from CLAUDE.md + David's testing policy): unit + integration + e2e tiers per component are mandatory; only _redundancy_ is removed — a test is removable only when the behavior it asserts is provably covered elsewhere (shared-module suite or a surviving test in the same bundle).

### 2a. Trim plan (from the test-trim-audit survey)

Baseline decomposition: 949 tests in 13 three-tier-file charts, 1,368 in 17 single-file charts, 256 in shared modules (= 2,573 exactly). No `it.each` inflation exists. Three redundancy classes are safe; a fourth (thinning e2e twins of integration tests) is **rejected** — e2e's full-pipeline narrative is the tier's value.

Execute (safest-first, all within-chart, no shared-module suite touched):

1. **Theme-enumeration collapse 4→1** in 26 unit files (~76 tests): each block's four per-palette tests assert only that the `@api theme` string round-trips — one identical code path. Palette contents stay covered in `themeService.test.js`; theme→mark wiring stays covered in integration tiers where it exists.
2. **advancedConfig duplicate branches** (~23 tests): drop `empty string` (the default-parse path again) and `whitespace-only` (the catch path again); keep one valid-parse + `invalid gracefully`.
3. **customColors no-crash unit dupes** (~11 tests): the unit variant asserts nothing beyond the valid-parse path; actual custom-color wiring is integration-covered.

Expected result: **~2,463 tests**, every component keeps unit + integration + e2e, zero functional coverage lost.

**Coverage gaps the audit exposed (addressed, not deferred):** (a) the 17 single-file charts never assert that a theme change reaches rendered marks — each chart touched by Workstream B or D gains one theme→color wiring test, which more than pays for its trimmed enumeration; (b) same for `colorMode` on treemap; (c) confirm gauge/heatmap/progressBar/sparklineGrid theming is genuinely covered by their bespoke describe blocks; (d) graphql-path coverage exists only on bar/gantt today — Workstream D adds a `.graphql.test.js` per converted chart by construction.

## 3. Workstream B — Quality fixes

Target: the charts the quality audit ranks weakest, brought up to current conventions with the smallest change that fixes each defect. `d3Choropleth`'s ROADMAP "In Progress" status gets resolved (finish or re-document as done).

### 3a. Fix plan (from the chart-quality-audit survey)

**Governing decision — wire, don't remove.** The audit found the dominant defect class is _advertised-but-unwired surface_ (drill-down trios, "Color Theme" pickers, `showLegend` stubs). Deleting these would (a) be semver-breaking, (b) hit the live-page `<property>`-removal deploy block, and (c) violate the fix-root-cause rule. So every dead control gets implemented using an in-repo proven donor pattern; only false _description text_ is corrected (meta descriptions are freely editable — no deploy risk).

**Tier 1 — functional bugs (must fix):**

- `d3Sankey`: adopt the standard `chartRendered = this.initializeChart()` + `createLayoutRetry` lifecycle (it's the only chart missing it; currently blanks permanently if first paint is zero-width in an inactive tab/accordion). Copy `d3BarChart`'s pattern exactly.
- `d3Gauge`: add `hasData` getter + no-data template branch; gate the SVG on it (currently paints a min-pinned gauge on empty data and renders under the spinner).
- `d3BulletChart`: fix `hasData` (currently `!error && d3 !== null` — the no-data branch is unreachable; empty data shows an empty chart).
- `d3LineChart`: delete the duplicate SVG legend (keep the accessible HTML one; reclaim the 30px margin reservation).

**Tier 2 — wire advertised drill-down** (donor: `d3BarChart.handleBarClick` → `NavigationMixin.Navigate`): BoxPlot (box click), CalendarHeatmap (day-cell click + `aria-label` the year-nav buttons), SparklineGrid (row click; also wire its allocated-but-never-shown tooltip), RadarChart (vertex click), and thread the lone dead `filterField` into the click payload for Treemap, Sankey, Histogram (adding the standard click where absent).

**Tier 3 — wire advertised theming/legends:** `theme` picker made real on Heatmap, CalendarHeatmap, Choropleth (theme → sequential-ramp hue family via a new shared `themeService` helper) and on WaterfallChart, DivergingBarChart (theme → semantic positive/negative variants); DivergingBar `customColors` override wired. Real HTML legends (Donut's copyable pattern) replace the empty `renderLegend` stubs in BarChart + HorizontalBarChart.

**Tier 4 — doc-drift + Choropleth finish:** meta `advancedConfig` descriptions synced to actually-consumed keys both directions (remove false Funnel `showGrid`/`showLegend`, Heatmap `showGrid`, Treemap `showTotal` claims; document Bullet ×4, Gauge `minValue`/`maxValue`, Radar/Sparkline/Pie `customColors`/`minLabelAngle`, Choropleth `noDataColor`, HorizontalBar `legendPosition`). Choropleth: remove `world` from the picklist datasource (the option throws today; datasource-value edit, not a property removal — implementer verifies deploy), align `borderWidth` meta/JS defaults, expose `hoverBorderWidth`/`midColor` (additions are always safe), wire `theme`, flip ROADMAP to Done.

**Tier 5 — cross-cutting consistency (applied per chart during B/D passes):** delete dead donor CSS (`.chart-tooltip`, `.slds-alert_warning`) everywhere; add minimal `.css` (svg `font-family: "Salesforce Sans"` + hover states) to the 9 CSS-less charts; accessibility baseline via a shared `chartUtils` helper (`role="img"` + `<title>`/`<desc>` per svg; keyboard-operable legends on Donut/Pie/Area; `role="progressbar"` + `aria-value*` on ProgressBar); Treemap switches to shared `getContrastColor`; Lollipop regains its `_configParsed` field declaration.

Every wired feature lands with tests (including the theme→color wiring test the trim audit found missing in the 17 single-file charts).

## 5. Workstream D — GraphQL `fetchMode` everywhere (A-pattern)

The additive pattern shipped in v1.1.0 on `d3BarChart`: `@api fetchMode` = `auto` (default, backward compatible) | `apex` | `graphql`, self-fetching via the v2 `lightning/graphql` wire through the shared `graphqlService` builders/normalizers — no Apex involved in graphql mode, FLS/sharing enforced by the platform.

Applies to all 28 existing charts except `d3BarChart` (already A) and `d3GanttChart` (already B, untouched). The 10 new charts implement it natively.

### 5a. Conversion recipe (from the graphql-recipe survey)

Reference trio for every converting agent: `d3BarChart/{d3BarChart.js, d3BarChart.js-meta.xml, __tests__/d3BarChart.graphql.test.js}` + `graphqlService/graphqlService.js` + `__mocks__/lightning/graphql.js`. The A-pattern elements, all additive:

1. Imports: `gql, graphql` from `lightning/graphql`; the shape-appropriate builder/normalizer pair from `c/graphqlService`; add `wire` to the lwc import. Keep all Apex imports.
2. `@api fetchMode = "auto"` (never `dataSource` — LWC1107 forbids `data`-prefixed `@api`) + `@api graphqlFilter` (structured `{field, operator, value}`, NOT exposed in meta.xml).
3. Reactive `get gqlQuery()` — returns `undefined` unless `fetchMode === "graphql"` AND required field props are set; `undefined` un-provisions the wire (this is the whole auto/apex bypass).
4. `@wire(graphql, { query: "$gqlQuery" })` handler: inert-guard on fetchMode, error formatting, normalize to the chart's native data shape, **`this.chartRendered = false`** after setting data (load-bearing — without it the SVG never initializes), `isLoading = false`.
5. `loadData()` early-returns in graphql mode; the imperative recordCollection → Apex → soqlQuery chain is untouched (in `auto`/`apex` behavior is byte-identical to today — `auto` never selects GraphQL; graphql is strictly opt-in).
6. meta.xml: add the `fetchMode` `<property>` (`datasource="auto,apex,graphql"`, default `auto`); apiVersion 65 required (all bundles already are); **never remove** an existing `<property>` (live-page deploy block).
7. Tests: a dedicated `<chart>.graphql.test.js` per chart modeled on bar's (v2 wire stub via `__mocks__/lightning/graphql.js` + moduleNameMapper, live-verified aggregate envelope fixture `uiapi.aggregate.<Object>` with the `aggregate {}` wrapper per node; record envelope `uiapi.query.<Object>.edges[].node.<field>.value`), happy path + wire-error path minimum; extend `graphqlService.test.js` for any new builder/normalizer.

### 5b. Per-chart classification & shared-service additions

**Existing builders suffice (9 charts, convert directly):** donut, pie, horizontalBar, lollipop, funnel, radar, divergingBar, waterfall (+ client `computeRunningTotal` on normalized output), choropleth — all bar-identical `buildAggregateQuery`/`normalizeAggregate`. Treemap and sunburst single-level branches too.

**New shared primitive #1 — `buildMultiGroupQuery` + `normalizeMultiGroup`** (two-field grouped aggregate → `[{label, series, value}]`, the shape `getMultiGroupData`/`aggregateSeriesData` already produce): unlocks stackedBar, heatmap, chord, sankey, and the two-level branches of treemap + sunburst. **Gate: envelope verified against a live org before dependent charts merge** (the same gate that caught the bar-chart envelope divergence).

**Record-shaped charts (8): `buildRecordQuery` + thin normalizers + existing client-side computation:** line, area (date/value/series), calendarHeatmap (date/value), sparklineGrid (entity/date/series), scatter (XY + client Pearson — already implemented client-side), bubble (XY+size), histogram (values + client stats fallback — already implemented), boxPlot (raw grouped values + client `computeQuartiles`). No new envelope risk — the record envelope is live-verified (gantt).

**Value-only charts (3): gauge, bullet, progressBar** — no groupBy, so the aggregate builder doesn't fit. Decision: `buildRecordQuery` + client-side reduce (reuses the verified record envelope; avoids a new unverified groupless-aggregate envelope). CHART_LIMITS truncation applies as everywhere; documented.

**Count-based aggregation (waffle + any chart with operation=Count):** `buildAggregateQuery` supports Sum/Average/Min/Max only. Decision: in graphql mode with `operation=Count`, fetch records via `buildRecordQuery` and count client-side (same verified-envelope reasoning). A UI-API-native COUNT extension is a possible later optimization, only with live verification.

**d3ForceGraph (weakest fit):** attempt conversion ONLY if its existing Apex path is flat-record-shaped (one query feeding the client-side graph builder) — then `buildRecordQuery` is symmetric and it converts like the others. If it genuinely requires two related queries, defer with a documented "fetchMode not supported" note. The assigned implementer verifies which, first.

Net: 28 charts get `fetchMode` (27 firm + forceGraph conditional), 10 new charts ship with it natively, bar keeps A, gantt keeps B.

## 7. Verification & release

1. Full jest suite green at every merge point; final run recorded in the release notes.
2. `npx eslint` clean over every touched directory (repo-wide `npm run lint` is known-broken).
3. Sample live smoke: deploy `force-app` to the `AGENT` org if authenticated; verify a representative sample (1 converted old chart in graphql mode, 1 new chart, choropleth if touched) renders with zero console errors. If AGENT is unavailable, the release notes say so explicitly and live verification becomes a listed follow-up.
4. Release via the releasing-software flow: version 2.0.0 → 2.1.0 in package.json, CHANGELOG entry, tag `v2.1.0`, GitHub release, push master.

## 8. Execution model

Subagent-driven development (David's standing preference): each workstream decomposes into implementer subagent tasks with per-task spec + code review, batched in parallel where files don't overlap (charts are file-disjoint bundles — ideal for parallel implementers). Order: A (trim) → B+D interleaved per chart (a chart's quality fix and its fetchMode conversion are done by the same agent to avoid double-touching) → C (new charts, parallel batches) → E (docs) → release.

Conflict rule: exactly one agent owns a component directory at a time; shared modules (`graphqlService`, `dataService`, `chartUtils`) are only touched by a designated agent per module, never in parallel.
